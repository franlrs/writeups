// 01

Summary

Appointment is the first machine of HackTheBox Starting Point Tier 1. It introduces the most foundational web attack: SQL Injection for authentication bypass. The target hosts a simple Apache web application with a login form that constructs an SQL query directly from user input, without sanitization or parameterized queries.

By injecting a single quote and a MySQL comment character into the username field, we can break out of the intended query logic and force the database to return a successful authentication result without ever knowing a valid password. This is classified as OWASP A03:2021 — Injection, the third most critical web application vulnerability category.

The injection payload admin'# causes the backend SQL query to comment out the password check entirely, granting admin access. The flag is displayed directly on the resulting dashboard page.

# Vulnerability Payload Impact
1 SQL Injection (Auth Bypass) admin'# in username field Authentication completely bypassed, admin access granted

// Why this works

The backend query likely looks like: SELECT * FROM users WHERE username='[INPUT]' AND password='[INPUT]'. Injecting admin'# transforms it into: SELECT * FROM users WHERE username='admin'#' AND password='...' — the # character starts a comment in MySQL, so everything after it (including the password check) is ignored. The query returns the admin row, and authentication succeeds.

Navigating to http://10.129.x.x presents a clean login form with username and password fields. We try a few default credentials first (admin/admin, admin/password) — all fail. The next step is to test whether the form is vulnerable to SQL injection by inserting a single quote into the username field.

Entering just ' (a single quote) in the username field causes the application to return an error or behave unexpectedly — confirming the input is being embedded directly into an SQL query without escaping.

Exploitation

1
SQL Injection payload — admin'#

We use the classic MySQL authentication bypass payload. The ' closes the username string, and # comments out the rest of the query including the password check.

SQLI PAYLOAD

Password: (anything — ignored)

// 06

Glossary

SQL Injection (SQLi)
SQL Injection occurs when user-supplied input is embedded directly into an SQL query without sanitization or parameterization, allowing an attacker to alter the query's logic. It is classified under OWASP A03:2021 — Injection and has consistently been one of the most critical web vulnerabilities for over two decades. Impact ranges from authentication bypass to full database dump to, in some configurations, remote code execution via xp_cmdshell (MSSQL) or INTO OUTFILE (MySQL). The only correct remediation is to use parameterized queries / prepared statements.
Authentication Bypass
An authentication bypass attack circumvents a login mechanism without knowing valid credentials. SQL injection-based bypass works by manipulating the underlying query so it returns a valid user record regardless of the password provided. Other bypass techniques include default credentials, JWT algorithm confusion, and insecure direct object reference (IDOR) on session tokens. The fundamental fix is to separate code from data — user input must never control query structure.
Parameterized Queries / Prepared Statements
Parameterized queries (also called prepared statements) are the correct defence against SQL injection. Instead of concatenating user input into an SQL string, the query structure is sent to the database separately from the data. The database driver handles escaping and type enforcement, making it impossible for user input to alter query logic. Example in PHP with PDO: $stmt = $pdo->prepare("SELECT * FROM users WHERE username = ? AND password = ?"); $stmt->execute([$user, $hash]);
