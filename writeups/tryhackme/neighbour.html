// 01

Summary

Neighbour is an Easy difficulty room from the TryHackMe platform. It is a pure web security challenge — no privilege escalation, no reverse shell — focused entirely on a single concept: Insecure Direct Object Reference (IDOR), categorised under OWASP A01:2021 — Broken Access Control.

The application simulates a small user-profile web service. A login page hints that a guest account is available, and a closer look at the HTML source code reveals the credentials hardcoded in a developer comment. Once authenticated, the URL exposes a user parameter that the server uses without any authorisation check — changing its value from guest to admin is all it takes to obtain the flag.

This room is ideal for understanding the fundamental difference between authentication (proving who you are) and authorisation (proving what you are allowed to do). Both must be enforced server-side; trusting user-supplied input for object access is the core mistake this room demonstrates.

// OWASP A01:2021 — Broken Access Control

Broken Access Control was ranked #1 in the OWASP Top 10 2021, appearing in 94% of tested applications. IDOR is one of its most common manifestations: when a web application uses user-supplied data to directly reference internal objects (database rows, files, account identifiers) without verifying that the requester is authorised to access them. The fix is always server-side: never rely on what the client sends to decide what they can see.

// 02

Reconnaissance

1
Port scan with Nmap

Start by deploying the machine on TryHackMe and noting the assigned IP. The first step is always a port scan to understand what services are exposed. This room runs a single web service — Nmap confirms port 80/tcp open.

BASH $ nmap -sV -sC -p- --open -oN neighbour.nmap 10.10.X.X
Starting Nmap 7.94 ( https://nmap.org )
PORT STATE SERVICE VERSION
80/tcp open http Apache httpd 2.4.x
| http-title: Neighbour
|_http-server-header: Apache

Service detection performed.

Only one port open: port 80 running an Apache web server. There is no SSH, no FTP, no database port — the entire attack surface is the web application. This tells us immediately to focus our attention on the browser.

2
Visit the web application

Opening http://10.10.X.X in the browser shows a login page. Notice the hint displayed below the form — the page itself tells us to use a guest account and suggests pressing Ctrl+U to view the source. This is the first clue in a chain of developer oversights.

// Developer hint — source code

When a web application instructs users to look at its own source code, that is both a CTF hint and a real-world red flag. Developers frequently leave credentials, internal endpoints, API keys, and TODO comments in HTML that gets shipped to production. Always read the source during a web security assessment.

// 03

Web Exploitation

1
Source code review — find credentials

Press Ctrl+U (or right-click → View Page Source) on the login page. Inside the HTML, immediately below the login form, there is a developer comment that was never removed before deployment:

HTML SOURCE <!-- use guest:guest credentials until registration is fixed.
"admin" user account is off limits!!!!! -->

The comment reveals two critical pieces of information: the guest:guest credentials to log in, and the confirmation that an admin account exists. The explicit warning "off limits" is, of course, exactly what we should try next.

2
Log in as guest

Enter guest / guest into the login form and submit. The application authenticates successfully and redirects to the user profile page. Observe the URL bar — this is where the vulnerability becomes visible.

http://10.10.X.X/profile?user=guest

The user parameter is passed via the URL query string and used by the server to determine which profile to display. The application trusts this value entirely — there is no server-side check confirming that the authenticated session matches the requested profile. This is the definition of an IDOR vulnerability.

// Vulnerability confirmed — IDOR

The server uses ?user=guest to fetch and display a profile without verifying that the logged-in session belongs to that user. Any authenticated (or even unauthenticated) request with a different username would be served the corresponding profile. The authorisation check is entirely absent.

// 04

IDOR Attack

1
Manipulate the URL parameter

With the IDOR identified, the exploit is trivial: modify the user parameter from guest to admin directly in the URL bar and press Enter. No special tools required — this is a one-character-change attack.

BROWSER URL # Change from:
http://10.10.X.X/profile?user=guest

# To:
http://10.10.X.X/profile?user=admin
2
Retrieve the flag

The server responds with the admin profile page — no additional authentication, no session check, no error. The flag is displayed directly on the page:

Welcome, admin!

Your flag: flag{neighbour_idor_pwned}

The flag confirms complete exploitation. The server rendered the admin profile for our guest session because it only used the user URL parameter as a database lookup key, with no cross-check against the authenticated session token.

// Why this works — the root cause

A correct implementation would perform a server-side session check: read the currently authenticated username from the session/cookie, and only return data for that user — ignoring or rejecting any ?user= parameter entirely. Exposing internal object references (usernames, IDs) in URLs and trusting them is always the root cause of IDOR. The fix is never client-side.

// 05

Command Reference

nmap
nmap -sV -sC -p- --open -oN <output> <IP>
Full port scan with service/version detection and default scripts. Essential first step on any target.
  • -sV — version detection
  • -sC — default NSE scripts
  • -p- — all 65535 ports
  • --open — show only open ports
  • -oN — save output to file
curl
curl -s http://<IP> | grep -i <pattern>
Fetch a page and pipe to grep to quickly spot credentials, comments, or hidden fields in the HTML source.
  • -s — silent mode (no progress bar)
  • -i — case-insensitive grep
  • -v — show response headers
  • -L — follow redirects
Browser DevTools
Ctrl+U / F12 → Elements / Network
View the raw HTML source and intercept requests. Faster than curl for interactive exploration; reveals comments, hidden inputs, and inline scripts.
  • Ctrl+U — view page source
  • F12 — open DevTools
  • Ctrl+Shift+I — Elements panel
  • Network tab — inspect all requests
URL Parameter Fuzzing
ffuf -u http://<IP>/profile?user=FUZZ -w wordlist
Automate IDOR discovery by fuzzing known parameters with a username or ID wordlist. Useful when account names are not known in advance.
  • -u — target URL with FUZZ keyword
  • -w — wordlist path
  • -fc 403 — filter forbidden responses
  • -mc 200 — match only HTTP 200

// 06

Glossary

IDOR — Insecure Direct Object Reference
IDOR is a type of access control vulnerability that occurs when an application uses user-supplied input to directly access objects — database rows, files, account records — without verifying that the authenticated user is authorised to do so. The "object reference" is direct because it maps to an internal identifier (username, numeric ID, filename) and insecure because the server trusts it blindly. In this room the reference is ?user=guest, and changing it to ?user=admin is sufficient to bypass all access controls. IDOR falls under OWASP A01:2021 — Broken Access Control, the number-one web vulnerability category.
Broken Access Control — OWASP A01:2021
Access control enforces policies that prevent users from acting outside their intended permissions. Broken access control means those policies fail — either they are missing, poorly implemented, or can be bypassed by manipulating client-side inputs. OWASP reports it in 94% of audited applications, making it the most pervasive web vulnerability class. Common manifestations include: IDOR, forced browsing to authenticated pages, privilege escalation via parameter tampering, and missing function-level access control. The fix is always server-side enforcement — the client must never be trusted to declare its own permissions.
Authentication vs. Authorisation
Two concepts that are often confused but must both be correctly implemented. Authentication answers "Who are you?" — it verifies identity (username + password, token, certificate). Authorisation answers "What are you allowed to do?" — it enforces permissions after identity is established. In the Neighbour room, authentication works correctly (guest:guest logs in), but authorisation is completely absent (any logged-in user can access any other user's profile). Passing the authentication check does not mean a user is authorised to access every resource.
Source Code Review — Developer Comments
HTML comments (<!-- ... -->) are visible to anyone who inspects the page source, but are not rendered in the browser. Developers routinely leave sensitive information in comments: credentials, internal hostnames, API endpoints, disabled features, and implementation notes. This is a common finding in web penetration tests and bug bounty programmes. Best practices require automated secrets-scanning in CI/CD pipelines to detect and block commits that include hardcoded credentials or sensitive data before they reach production.
URL Query Parameters
Query parameters are key-value pairs appended to a URL after the ? character, separated by &. Example: /profile?user=guest&theme=dark. They are fully user-controlled — any user can modify them in the browser address bar, via DevTools, or with tools like Burp Suite or curl. When server-side logic uses query parameters to determine what data to return (e.g., SELECT * FROM profiles WHERE username = ?user), the application must validate that the requesting session has permission to access that data. Omitting this check is a textbook IDOR.
HTTP Session Tokens & Cookies
After a successful login, a web server issues a session token (typically stored in a cookie) that identifies the authenticated user on subsequent requests. A correct authorisation implementation reads the username from this server-side session — not from a URL parameter — and only serves data belonging to that session user. The session token must be HttpOnly (inaccessible to JavaScript), Secure (HTTPS only), and SameSite (CSRF protection). In the Neighbour room, the session is valid but the server ignores it when deciding what profile to display, relying entirely on the attacker-controlled ?user= parameter instead.
